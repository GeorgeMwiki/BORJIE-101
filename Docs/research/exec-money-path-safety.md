## PART 1 — IDEMPOTENCY KEYS + IDEMPOTENT RECEIVERS

**SOTA (June 2026).** Idempotency key = client/caller-generated V4 UUID or high-entropy string; the server stores it in a **durable** store (Postgres / Redis-AOF, never memory-only — "one pod restart and your guarantee is gone") under a UNIQUE constraint; a retry returns the *cached original response*. The non-obvious frontier rules: (1) **the key must be generated by the originator, not the server** — a server-minted key produces a *new* key on retry-after-timeout and silently bypasses dedup; (2) **pin the key to a canonical hash of the request body** (sorted-key, minified JSON) and *reject* a reused key whose payload differs — clients re-serialise JSON with different key order, so hashing the raw body is the classic false-mismatch pitfall; (3) **24h TTL** is the retail sweet spot (Stripe, Razorpay); (4) webhook receivers dedup on the *provider event id*, independently, because delivery is at-least-once. ([Stripe idempotency](https://docs.stripe.com/api/idempotent_requests), [Stripe blog](https://stripe.com/blog/idempotency), [NxtBanking patterns & pitfalls](https://nxtbanking.com/idempotency-keys-payment-api-design/), [Simplico 2026-04](https://simplico.net/2026/04/04/idempotency-in-payment-apis-prevent-double-charges-with-stripe-omise-and-2c2p/))

**Borjie state vs SOTA.** We already nail (1)-(3) at the ledger engine: `postJournalEntry({idempotencyKey})` is backed by a UNIQUE `(tenant_id, idempotency_key)` and the `IdempotencyMismatchError` is precisely the "reused key, different legs ⇒ refuse loud" rule — implemented via order-independent `legSignature()` comparison (the canonical-hash idea, but on the *financial substance* of the legs rather than raw JSON, which is strictly better: it survives re-serialisation AND the same-account-fold case). Disbursement derives its transfer key (`disbursement-transfer:${disbursementId}`) and its Daraja `originatorConversationId` from the disbursement id — server-derived but **stable across retries** because the disbursement id is persisted PENDING before any money moves, so it satisfies the spirit of rule (1).

**The gap + the wire.** The *engine* is correct; the **gateway ingress** is where we must enforce SOTA rule (1)+(2) as policy. Wire: a single `Idempotency-Key` middleware on every money-mutating Hono route (`POST /payments/*`, `/disbursements`, `/bids/*/accept`, filing triggers) that (a) **requires** the header (reject 400 if absent on a money mutation — no server-minted fallback for client-originated calls), (b) stores `(tenant_id, key, request_body_hash, response_snapshot, status, created_at)` in a durable idempotency table with a UNIQUE `(tenant_id, key)`, (c) on replay with a *matching* body-hash returns the stored response, (d) on replay with a *divergent* body-hash returns `409 IDEMPOTENCY_KEY_REUSE` — mirroring Stripe's behavior and our engine's `IdempotencyMismatchError`. The key passed to the route then becomes the `idempotencyKey` threaded into `postJournalEntry`, so the gateway dedup and the engine dedup are the *same* key end-to-end (defense-in-depth, not two unrelated guards).

**SAFETY RAIL added:** *No client retry, network blip, or replica restart can double-post or double-pay, and a key can never be smuggled onto a different transaction.* The body-hash pin closes the "reuse a key for a different transfer and get back the wrong money" attack at the membrane, before it ever reaches the ledger.

## PART 2 — TRANSACTIONAL OUTBOX + INBOX + DEDUP (exactly-once-EFFECT under at-least-once delivery)

**SOTA (June 2026).** The outbox guarantees **at-least-once delivery, never exactly-once** — the canonical failure is: relay publishes → broker acks → relay crashes before marking `published` → on restart it republishes. Therefore **exactly-once-EFFECT = at-least-once delivery × idempotent receiver**, and the receiver dedups on a `message_id`/`event_id` it persists in an **inbox** table inside the same transaction as its own state change. Best-practice outbox table: `message_id` UUID (idempotency), `aggregate_id` (ordering/partition key), index on `(status, created_at)`, business-write + outbox-write in ONE tx, resilient relay (retry + backoff), lag monitoring (alert if stuck), cleanup/archival. CDC (Debezium reading the WAL) is the lowest-latency relay; polling is simpler but adds latency. ([microservices.io outbox](https://microservices.io/patterns/data/transactional-outbox.html), [AWS Prescriptive Guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html), [The Excited Engineer — outbox/inbox](https://theexcitedengineer.substack.com/p/guaranteeing-message-delivery-distributed), [James Carr 2026-01](https://james-carr.org/posts/2026-01-15-transactional-outbox-pattern/))

**Borjie state vs SOTA.** The **producer side is frontier**: money-path events co-commit *inside* `postJournalAtomic`'s `db.transaction` (not a second tx), with `event_outbox.sequence_number` assigned via a correlated subquery *inside the INSERT* (no SELECT-MAX-then-INSERT race), `onConflictDoNothing()` on the PK as a re-emit backstop, and `getUnpublished/markPublished/recordFailure/cleanup` as the relay surface. This is exactly the SOTA producer.

**The gaps + the wires.**
1. **Inbox / consumer-dedup is the weak side.** We have the outbox; the SOTA pair is an **inbox** table so every *consumer* (statement generator, disbursement reconciliation, downstream brain-tool that reacts to `LEDGER_ENTRIES_CREATED`) records `(consumer_name, message_id)` UNIQUE inside the same tx as its effect, and skips a message it has already processed. **Wire:** add an `event_inbox` table (migration, append-only) + a tiny `withInbox(consumerName, messageId, fn)` helper that the consumers wrap their handler in; processing is a no-op on a duplicate `message_id`. This converts our at-least-once relay into exactly-once-effect for *every* reactor, not just the ledger itself.
2. **Non-money services still write outbox on a SEPARATE tx.** The outbox repo's own doc flags it: statement/disbursement/reconciliation/payment-orchestration call `DurableEventPublisher.publish` on the top-level client, not co-committed with their business write (flagged `EXEC-saga`). **Wire:** thread the bound `txDb` into those services so their outbox row co-commits with their state change, exactly as the ledger already does (`serializeForTx` → `outboxRows` passed into the atomic call). This is mechanical — the pattern exists; copy it.
3. **Relay liveness + lag SLO.** Add the SOTA monitor: alert when `event_outbox` has rows with `published_at IS NULL` older than N seconds (relay stuck / dead), and a max-retry → dead-letter transition (`recordFailure` already increments retry; add a `dead` status + operator inbox surface above a threshold so a poison event never blocks the queue head).

**SAFETY RAIL added:** *A crash between "money durable" and "event delivered" can never drop a money event (producer co-commit), and a redelivered event can never apply its effect twice (inbox dedup).* Lag monitoring means a stalled relay is an alert, not a silent loss.

## PART 3 — SAGA / COMPENSATION + THE REVERSIBILITY-TYPED ACTUATOR (the keystone)

**SOTA (June 2026).** A saga replaces a distributed ACID transaction with a sequence of local transactions, each with a **compensating action** — and **compensation is NOT rollback**: it is a *new* forward transaction that semantically reverses the effect (you cannot rollback a wire that already left). The pivotal SOTA concept is the **pivot transaction**: the boundary between *compensable* steps (everything before the pivot is undoable) and *retryable* steps (everything after is forward-retried, never undone). **Orchestration** (a central controller drives the steps) beats choreography for money because complex conditional logic + auditability + visibility matter more than decoupling. ([microservices.io saga](https://microservices.io/patterns/data/saga.html), [Azure saga](https://learn.microsoft.com/en-us/azure/architecture/patterns/saga), [Temporal saga guide](https://temporal.io/blog/mastering-saga-patterns-for-distributed-transactions-in-microservices), [ByteByteGo orchestration vs choreography](https://blog.bytebytego.com/p/saga-pattern-demystified-orchestration))

**The Borjie design — reversibility in the TYPE.** This is the architectural move that makes the mandate *structural instead of review-dependent*. The actuator port carries, per action:
```
type PortAction = {
  kind: 'POST_LEDGER' | 'B2C_TRANSFER' | 'FILE_GEPG' | 'SEND_SIGNATURE_REQUEST' | ...
  reversibility: 'reversible' | 'compensable' | 'irreversible'
  idempotencyKey: string            // stable, derived from the saga step id
  dryRun: boolean                   // plan/preview without effect
  confirm?: FourEyeApprovalToken    // required iff requiresApproval(action)
  compensate?: (ctx) => PortAction  // the forward-reversing step
}
```
The invariant `irreversible ⇒ requiresApproval ⇒ four-eye` then **falls out of the type system**: a step typed `irreversible` is *uncompilable* without a `confirm` token, and the saga executor refuses to run it until the four-eye PROPOSE→APPROVE has produced one. This is the "governed autonomy, not open-ended inference" the 2026 finance-AI literature insists on ([Auditoria — governed autonomy](https://blog.auditoria.ai/finance-ai-2026-governed-autonomy)).

**The gap + the wire.** We have the durable *runner* (checkpoint/retry/recover) but it explicitly excludes compensation, and there is **no saga executor file**. Build a **Postgres-journalled saga executor** (DBOS-style — see Part 5 — so each step's checkpoint co-commits with its effect) that:
- walks `PortAction[]`; for each step records a `saga_step` row (`pending→running→done|compensating|compensated|gated`) *in the same tx as the step's local effect where the effect is a DB write*;
- on a step failure runs `compensate()` for every **compensable** step *in reverse order* (the pivot boundary: ledger posts before the pivot are compensable via reversing journals; the external transfer is the pivot/retryable);
- on hitting an `irreversible` step without a `confirm`, transitions to **`gated`** (our existing `paused`), emits the four-eye PROPOSE, and **resumes from that exact step** when the APPROVE token arrives — this is precisely the LangGraph `interrupt()`+checkpointer HITL pattern that is the 2026 production substrate ([MyEngineeringPath HITL 2026](https://myengineeringpath.dev/genai-engineer/human-in-the-loop/));
- binds saga **receipts into the existing hash-chained audit chain** (append-only).

**Concrete money-path sagas this unlocks (each = a `PortAction[]`):**
- **Disbursement saga:** `[POST_LEDGER(compensable, compensate=reversing-journal), B2C_TRANSFER(pivot/retryable, idem=disb-id)]` — formalises the already-correct ledger-before-transfer ordering, and turns today's `NEEDS_REVERSAL` terminal state into an *automatic* compensation (reverse the debit) or *confirmed re-drive* (retry the transfer under the same key) decision the executor owns.
- **GePG royalty/levy filing saga:** `[POST_LEDGER(compensable), FILE_GEPG(irreversible ⇒ requiresApproval, idem=control-number)]` — the filing is a four-eye step *by type*, and `FILE_GEPG` is the kind already reserved in `action-runtime.schema.ts:127`.
- **E-signature saga:** `[SEND_SIGNATURE_REQUEST(irreversible ⇒ four-eye), SIGN_COMPLETE(webhook receiver marks step COMPLETED)]`.

**SAFETY RAIL added:** *No multi-step money flow can stop half-done. Either every step completes, or the compensable prefix is forward-reversed and the ledger nets to its pre-saga state — provably (the saga journal + the ledger hash-chain together are the proof). And no irreversible filing/payout can fire without a four-eye token, because the executor cannot type-check the step without one.*

## PART 4 — IMMUTABLE DOUBLE-ENTRY INVARIANTS + RECONCILIATION / ATTESTATION

**SOTA (June 2026).** Enforce the invariant **at the database transaction layer, not in app code** — "no partial failure can produce an unbalanced entry"; balances are *derived* from append-only journal entries, never stored as a mutable number that can drift; corrections are **reverse-then-re-post** (or post the delta), never an UPDATE; the SOTA fintech split is **mutable business objects vs immutable accounting objects** with a **pending (mutable) → posted (immutable)** state transition; the operationally-critical loop is **continuous reconciliation** ("days to seconds") that verifies records across systems agree. ([Modern Treasury — enforcing immutability](https://www.moderntreasury.com/journal/enforcing-immutability-in-your-double-entry-ledger), [Trio — payment ledger architecture](https://trio.dev/payment-ledger-architecture-fintech/), [Griffin — immutable bank](https://griffin.com/blog/the-immutable-bank), [Blnk](https://www.blnkfinance.com/))

**Borjie state vs SOTA.** We **exceed** the article on tamper-evidence (Modern Treasury explicitly does *not* hash-chain; we do, per-account, with `verifyHashChainForAccount`). We have balanced-or-reject (`validateJournalBalance`), reverse-then-re-post (`postCorrectionEntry`/`voidEntry` never mutate), derived-balance verification (`verifyAccountIntegrity` recomputes from entries and reports the discrepancy), and sequence-gap detection. The **store-the-balance** risk the SOTA warns about is mitigated because our stored balance is CAS-guarded against the version and *cross-checked* by `verifyAccountIntegrity`.

**The gaps + the wires.**
1. **Push the balanced invariant INTO Postgres.** App-layer `validateJournalBalance` is correct but is one bug away from being bypassable. Add a **deferred CHECK / constraint trigger** that asserts `SUM(debits) = SUM(credits)` per `journal_id` at COMMIT, and a column constraint forbidding negative amounts — so even a future direct-write code path (which the mandate forbids, but defense-in-depth) cannot land an unbalanced journal. This is the SOTA "enforce at the DB layer" move.
2. **Continuous reconciliation + daily attestation.** We have `reconciliation.job.ts` and `disbursement-reconciliation.job.ts`; raise them to a **continuous trial-balance attestation**: a scheduled job that (a) re-derives every tenant's account balances from entries and asserts `== stored`, (b) asserts the platform-wide **sum-to-zero** (every debit has its credit), (c) re-verifies the hash-chain head per account, (d) writes a signed `attestation` row (date, tenant, balances-hash, chain-head, PASS/FAIL) into an append-only attestations table, and (e) pages on any FAIL and *fail-closed* halts disbursements for that tenant until cleared. This is the "reconciliation from days to seconds" loop plus a signed daily proof an auditor/regulator can verify.
3. **Pending→posted explicit state.** Adopt the SOTA pending/posted split for entries that depend on external settlement (M-Pesa STK callback, bank clearing): an entry is `pending` (excluded from available balance, mutable/cancellable) until the provider confirms, then `posted` (immutable, in the chain). This prevents counting un-cleared money as disbursable.

**SAFETY RAIL added:** *The ledger cannot hold an unbalanced or negative journal even under a future code regression (DB-layer constraint), and a silent balance drift cannot survive a single reconciliation cycle — it is caught, paged, and disbursements fail-closed until reconciled, with a signed daily attestation as the audit artifact.*

## PART 5 — DURABLE EXECUTION (crash-resumable money steps): Temporal vs Inngest vs DBOS

**SOTA (June 2026).** Durable-execution engines run code to completion across crashes, auto-resuming from the last completed step. The decisive 2026 distinction for *money*: **DBOS achieves exactly-once for DB-bound steps natively** by committing the step's effect AND its checkpoint in **one Postgres transaction** ("piggyback the step checkpoint as part of the transaction") — so a crash either rolls back both or commits both, and on restart the step is *definitively not re-executed* without requiring the step to be idempotent. Temporal/external orchestrators give **at-least-once** and require application-level idempotency; they're mature at scale but add a separate server + ~10× the code (>100 lines vs ~7). Restate sits between. ([DBOS — why Postgres durable execution](https://www.dbos.dev/blog/why-postgres-durable-execution), [Tiarebalbi — DBOS vs Temporal 2026](https://www.tiarebalbi.com/en/blog/dbos-vs-temporal-postgres-durable-execution), [DevNote — Temporal/Restate/DBOS 2026](https://devstarsj.github.io/2026/04/03/durable-execution-temporal-restate-dbos-distributed-workflows-2026/), [Supabase — DBOS on Postgres](https://supabase.com/blog/durable-workflows-in-postgres-dbos))

**The Borjie decision (recommended).** We are **already a Postgres-centric, single-database, RLS-governed** system. The DBOS model is therefore the *natural fit* and the safest for the money path: **co-commit the saga step checkpoint with the step's ledger effect in the same `db.transaction`** — which is *exactly the mechanism `postJournalAtomic` already uses* for outbox co-commit. We do **not** need to adopt the DBOS library wholesale; we need to adopt its *invariant* (checkpoint ⊆ effect tx) in our own saga executor (Part 3). Keep the **Temporal workflows** we already have (KRA/eRITS/MRI/licence-suspension) for the **long-running, external-polling, batch** flows where Temporal's timers/signals/queries earn their cost — but their *money-touching* steps must still post through `LedgerService.post` via an activity, never write the ledger directly. The Inngest path on the durable-runner stays as the optional dispatch backend for the agency loop.

**The gaps + the wires (these are the master-plan BLOCKERS OK-5/OK-6).**
1. **Instantiate the durable runner + flip `DURABLE_EXEC_ENABLED`** so the default agency/money path runs ON the durable runner, not the bail-on-first-failure linear executor. The runner exists and is tested — it is simply never `createDurableRunner(...)`-called in `index.ts`.
2. **Build the saga executor (Part 3) on the DBOS invariant** — checkpoint co-committed with each DB-bound step's effect; for external-effect steps (transfer/filing), the checkpoint records "intent + idempotency key" *before* the external call and "outcome" *after*, so a crash mid-call resumes by *re-driving under the same key* (the external provider's idempotency dedups), never by re-deciding.
3. **Wire the filing workflows' placeholder activities** to the real GePG/KRA connectors (Part 7), keeping the money leg on `LedgerService.post`.

**SAFETY RAIL added:** *A process crash at any instant — before, during, or after a money step — resumes deterministically from the last durable checkpoint with no double-effect and no lost step. For DB-bound steps the guarantee is exactly-once by construction (checkpoint ⊆ effect tx); for external steps it is at-least-once-delivery × idempotent-key = exactly-once-effect.*

## PART 6 — DUAL-CONTROL / HITL GATE FOR IRREVERSIBLE ACTIONS

**SOTA (June 2026).** The **four-eyes / maker-checker** principle (initiator ≠ approver) is the canonical control for irreversible money/licence/deletion actions, now extended to AI agents: HITL is mandatory when the action is **irreversible, carries legal/compliance risk, or the agent's confidence is below a calibrated threshold**. The 2026 production substrate is **LangGraph `interrupt()`**: pause the graph at a node, **persist state to a checkpointer**, resume only on the human response. The **EU AI Act Article 14 (enforceable 2026-08-02)** *mandates* human-oversight capability for high-risk AI. Coinbase's agent-wallet guardrails (session caps, transaction limits, operation allowlists, **multi-party approvals**, audit logs) are the emerging payment-agent template. ([MyEngineeringPath HITL 2026](https://myengineeringpath.dev/genai-engineer/human-in-the-loop/), [Strata HITL 2026 guide](https://www.strata.io/blog/agentic-identity/practicing-the-human-in-the-loop/), [aico.ai four-eye](https://aico.ai/glossary/four-eye-principle), [Galileo — HITL agent oversight](https://galileo.ai/blog/human-in-the-loop-agent-oversight))

**Borjie state vs SOTA.** We have a four-eye spine (`services/mcp-server-borjie/src/four-eye.ts`, `auto-authorize-gate`, sovereign HITL in `sovereign.ts`/`brain-kernel-wiring.ts`). The SOTA upgrade is to make the gate **structural and confidence-aware** rather than a code-path check.

**The wire.** Two pieces, both already half-present:
1. **Type-level gate (Part 3):** `irreversible ⇒ requiresApproval` is enforced by the actuator `PortAction` type; the saga's `gated` state IS the `interrupt()`+checkpointer pause, and our durable checkpoint store IS the checkpointer. Resume-from-gated-step on APPROVE is the same resume path the runner already has.
2. **Confidence threshold (the EstateMind actuator bridge, OK-4):** the master plan already states a motivated autonomous goal must cross `confidence × (1 − reversibility)` before it emits an `OrchestratorRequest`. Make that the *same* threshold that decides four-eye: below it, the action is *proposed* to a human, never auto-executed. This is the calibrated-confidence rule the 2026 HITL literature requires, expressed in our own units.

**SAFETY RAIL added:** *Every irreversible money/licence/deletion/filing action requires a second human (initiator ≠ approver), enforced by the type system and the saga gate — not by reviewer diligence. A low-confidence autonomous action is proposed, never executed. This is also our EU AI Act Art. 14 human-oversight evidence.*

## PART 7 — CIRCUIT-BREAKERS + BULKHEADS + GRACEFUL DEGRADATION ON THE CRITICAL PATH

**SOTA (June 2026).** **Circuit breaker** trips on failure-rate threshold and fast-fails subsequent calls (no thread parked on a dead dependency). **Bulkhead** isolates concurrency pools so one saturated dependency can't exhaust the shared pool — "critical paths should have larger bulkheads; non-critical features smaller." Use them **together** (breaker detects, bulkhead isolates). On rejection, **graceful degradation** > error. ([Medium — circuit breaker & bulkhead deep dive 2026-03](https://medium.com/codetodeploy/circuit-breaker-bulkhead-pattern-a-deep-dive-for-distributed-systems-6256a39eb269), [Zuplo — API gateway resilience](https://zuplo.com/learning-center/api-gateway-resilience-fault-tolerance), [Aerospike — circuit breaker](https://aerospike.com/blog/circuit-breaker-pattern/))

**The Borjie wire (the subtle part — fail-OPEN vs fail-CLOSED differ by side of the money).**
- **Around external providers (M-Pesa Daraja, Stripe, GePG, e-sign, KRA):** wrap each in a circuit breaker with a *dedicated bulkhead*. On open-circuit, **do NOT degrade silently** — the saga step parks in its durable checkpoint (Part 5) and the reconciliation loop re-drives under the same idempotency key when the breaker half-opens. The breaker prevents a dead provider from parking gateway threads and cascading; the durable checkpoint prevents the breaker's fast-fail from *losing* the step.
- **Around `LedgerService.post` itself:** the breaker must **fail CLOSED** — if the ledger DB is unreachable, the *correct* behavior is to refuse the money action entirely (no transfer, no filing), never to degrade to "skip the ledger and move money anyway." This aligns with the kill-switch fail-closed mandate. A money action with no posting is the one outcome we never allow.
- **Read-path degradation is fine:** balance displays, statements, disbursement *previews* may serve cached/stale with a freshness banner when a dependency is down — that's the "degrade reads, never degrade money-effect" line.

**SAFETY RAIL added:** *A dead external provider fast-fails into a durable, resumable parked step (never a parked thread, never a lost step, never a blind re-send); a dead ledger fails the whole money action closed (never "move money without posting"). The critical path gets the big bulkhead; cosmetic reads degrade gracefully instead of erroring.*

## PART 8 — FINANCIAL-CORRECTNESS INVARIANTS ASSERTED CONTINUOUSLY + THE OUT-OF-PROCESS RAIL

**SOTA (June 2026).** Two convergent themes: (a) financial invariants (sum-to-zero, no-negative, append-only, balance==derived) must be **asserted continuously**, not just at write time — reconciliation is the most operationally critical fintech process; (b) for AI agents, every consequential action must pass an **out-of-process, signed, policy-versioned guardrail** that writes the immutable audit entry *first*, and a real **kill switch denies new tool calls immediately across the fleet** with a signed audit trail — guardrails must be unreachable from the agent loop even under prompt injection. ([Atlan — AI agent guardrails 2026](https://atlan.com/know/ai-agent-risks-guardrails/), [aport.io — kill switch guide](https://aport.io/blog/openclaw-guardrails-audit-ai-agents-kill-switch-guide/), [ARMO — securing AI agents in financial services](https://www.armosec.io/blog/financial-services-ai-agent-security/), [IMF 2026 — agentic AI in payments](https://www.elibrary.imf.org/view/journals/068/2026/004/article-A001-en.xml))

**The Borjie wire (master-plan OK-8b).** Extract policy-gate + inviolable + kill-switch + rate-limits + budget into an **out-of-process autonomy-controller** (sidecar/subprocess). Every external actuator call — `LedgerService.post`, B2C transfer, GePG filing, deletion, external comms, body-change — routes through it; it **writes the hash-chained decision-log entry FIRST, then permits the effect**, and is **unreachable from the agent loop even under prompt injection** (so a compromised in-process kernel cannot reach the rails). Combine with Part 4's continuous attestation: the rail decides *may this effect happen*, the attestation proves *the effects that happened are still consistent*. The kill-switch in front of the rail must **deny new money/actuator calls fleet-wide, fail-closed, signed** — never caught-and-ignored (mandate).

**SAFETY RAIL added:** *No money effect happens without a decision-log entry already written (decision-before-effect, hash-chained, append-only). A prompt-injected kernel cannot reach the rails because they live out-of-process. A kill-switch trip denies all new money actions fleet-wide and fails closed. Continuous attestation proves the resulting books still balance.*

## PART 9 — WIRING SEQUENCE (so we never fail at it) + EXECUTOR DISCIPLINE

The money-path wiring must land in **dependency order**, each step verified-then-committed on a clean tree, behind a flag until proven:

1. **Gateway idempotency middleware** (Part 1) + **`event_inbox` + consumer co-commit** (Part 2) — pure additive, no behavior change on the happy path; ships first, instantly raises the floor.
2. **DB-layer balanced/no-negative constraint + continuous attestation job** (Part 4) — additive, fail-closed only on a *real* drift; prove it pages on an injected discrepancy in a test tenant.
3. **Reversibility-typed actuator port + Postgres-journalled saga executor on the DBOS invariant** (Parts 3+5) — the keystone; build behind `DURABLE_EXEC_ENABLED`, bind as the default ACTUATE executor, port the disbursement flow onto it first (it is already ledger-before-transfer, so the saga formalises proven behavior).
4. **Four-eye-by-type + confidence threshold** (Part 6) — flows from the actuator type; wire the gated→approve→resume path through the existing checkpoint store.
5. **Circuit breakers + bulkheads** around each provider, **fail-closed around the ledger** (Part 7).
6. **GePG / e-sign as four-eye saga steps** (Part 7/Wave 7) — land AFTER the saga executor (they bind into it); each is `irreversible ⇒ four-eye` by type.
7. **Out-of-process autonomy rail + fleet kill-switch** (Part 8, OK-8b) — last, because it sits in front of all the above and must not be wired before the effects it guards are themselves correct.

**Executor discipline (non-negotiable for this lane):** every step is (a) **append-only** to schema (migrations immutable), (b) **flag-gated** until a restart-persistence + crash-resume + double-delivery test proves exactly-once-effect, (c) **money-path tests are the gate**: `ledger-durability`, `disbursement-ledger-before-transfer`, `outbox-cocommit`, `idempotency-store`, `webhook-durable-idempotency` already exist — extend them with a saga-compensation test and a four-eye-gated-resume test before any money flow flips to the new executor. **Never** flip `DURABLE_EXEC_ENABLED` in production before the canary tenant proves a forced mid-saga crash resumes with the books still balanced.

---

## PART 10 — THE ONE-PARAGRAPH VERDICT

Borjie's *atomic* money core (a single `LedgerService.post`) is already at or beyond June-2026 SOTA: balanced-or-reject, idempotent, CAS-guarded, hash-chained, with outbox co-commit and ledger-before-transfer disbursement. The wiring we "cannot fail" is the **orchestration layer above the post**: a reversibility-typed actuator saga (DBOS-invariant: checkpoint co-committed with the effect) that makes `irreversible ⇒ four-eye` structural, an inbox to make every consumer exactly-once-effect, DB-layer balance constraints + continuous signed attestation, fail-closed circuit-breaking around the ledger, and an out-of-process decision-before-effect rail with a fleet kill-switch. Build those — in the order above, flag-gated, test-gated, crash-tested — and the money path is provably-correct and crash-safe: it can never post a bad, duplicate, or lost entry.
