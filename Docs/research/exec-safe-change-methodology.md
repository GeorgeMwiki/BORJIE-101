## PART 0 — WHY THIS LANE IS THE WHOLE GAME

Borjie's 43 gaps are not 43 greenfield builds. The closure plan's own finding is *"we have the organs, we lack the joints."* That single fact dictates the methodology: **we are modifying a running system, not writing a new one.** Modifying a live system is a solved discipline with a 15-year canon (Feathers, Fowler, Hohpe, the continuous-delivery school) plus a sharp 2025–2026 layer for AI agents (shadow-mode rollouts, staged autonomy). The failure mode we must avoid is the one the plan explicitly warns against — *"we wire 43 point-to-point hacks and re-create the spaghetti"* — and the way you avoid it is to make **every** awakening obey the same five-move ritual rather than improvising per gap.

The substrate is already shaped for this. The composition root (`services/api-gateway/src/composition/`) is a textbook **composition root** in Robert C. Martin's sense — "the one place where a concrete adapter gets wired to an abstract port" ([Hexagonal Me](https://jmgarridopaz.github.io/content/hexagonalarchitecture.html), [Java Code Geeks 2025](https://www.javacodegeeks.com/2025/06/hexagonal-architecture-in-practice-ports-adapters-and-real-use-cases.html)). The dark capabilities are already behind named flags (`BORJIE_MODALITY_ARBITER`, `BORJIE_BODY_CHANGE`, `DURABLE_EXEC_ENABLED`) — verified live on this branch at `brain-kernel-wiring.ts:425`, `orchestrator-bindings.ts:1192`, and `central-intelligence/src/index.ts:89`. The stubs are already factory functions behind ports (`createStubEstateHandlerDeps` at `dispatch-router-wiring.ts:262`, `createLoopRunnerAdapter` at `orchestrator-bindings.ts:1281`). **The seams already exist. The methodology is: use them, never bypass them.**

## PART I — THE SEVEN PILLARS (survey), each mapped to OUR closure

### Pillar 1 — STRANGLER FIG: build the new beside the old behind a router, redirect piece by piece, never big-bang

**The pattern.** Instead of a risky full rewrite, you stand new functionality alongside the legacy system behind a routing layer (gateway/proxy/factory), incrementally redirect specific requests to the new path, and let the old system keep serving until it can be retired. The defining property is *business continuity during the transition* and *risk confined to a small slice* ([Thoughtworks](https://www.thoughtworks.com/en-us/insights/articles/embracing-strangler-fig-pattern-legacy-modernization-part-one), [Kai Waehner 2025](https://www.kai-waehner.de/blog/2025/03/27/replacing-legacy-systems-one-step-at-a-time-with-data-streaming-the-strangler-fig-approach/), [Anoop Dande, Dec 2025](https://medium.com/@kumar.anoop062/the-strangler-pattern-how-we-modernized-a-legacy-system-without-breaking-production-e0a44888427b)).

**Borjie application.** The dispatcher in `brain-kernel-wiring.ts` IS our routing layer; the modality-arbiter is the "traffic controller." We never delete the stub-and-fall-closed path before the real path proves out — we route a *slice* (one tenant, one modality branch, one `?override`) to the real runner and let the rest keep falling closed. Concretely for **OK-2** (loop-runner stub → real `runLoop`): the strangler "old leaf" is `createLoopRunnerAdapter`'s breadcrumb stub; the "new leaf" is the real `@borjie/loop-runner` binding; the router is the arbiter's WORKFLOW/LOOP branch (`:1063-1072`). We strangle by making the arbiter route only flagged requests to the real runner first, widening the slice as the match-rate holds.

**Safety rail it adds.** *No big-bang on the default `/ask` turn.* A bug in the real loop-runner can only ever touch the routed slice; the unrouted majority still falls closed (the safe default). This directly satisfies the closure-plan risk note on Wave 1 ("ship behind a canary + per-request override").

### Pillar 2 — BRANCH BY ABSTRACTION: one stable interface, two implementations co-existing, switch then delete

**The pattern.** Capture the interaction between client code and supplier behind an abstraction layer; build the new supplier against the *same* abstraction; switch consumers one at a time; delete the old supplier once nothing references it. Old and new coexist behind one interface so the system stays releasable the whole time ([Fowler](https://martinfowler.com/bliki/BranchByAbstraction.html), [OneUptime, Jan 2026](https://oneuptime.com/blog/post/2026-01-30-branch-by-abstraction-pattern/view)). The 2026 OneUptime write-up gives the exact five phases — *identify call sites → create abstraction → wrap legacy as an adapter → implement new provider → migrate consumers incrementally with DI* — and the hard rule: *"Write tests against the interface, not implementations. Run the same test suite against both implementations before considering migration complete."*

**Borjie application.** This is the default move for **every stub→real swap** because the abstraction already exists — the port. We do NOT edit call sites; we change *which adapter the composition root injects into the existing port*. For **OK-1 / Wave-1** the port is the loop-runner adapter type; for **OK-7** the port is `BodyChangePort` (`orchestrator-bindings.ts:1192` already has the deny-stub-vs-real fork *inside one function*, which is branch-by-abstraction in miniature — both implementations behind one `buildBodyChangePort` selected by the `BORJIE_BODY_CHANGE` flag). For **OK-6** the port is the durable runner selected by `DURABLE_EXEC_ENABLED`. The factory `createStubEstateHandlerDeps` (`dispatch-router-wiring.ts:262`) is *literally the legacy adapter* in OneUptime's phase 3 — we keep it, stand `createRealEstateHandlerDeps` beside it, and flip the factory selection.

**Safety rail it adds.** *Zero blast radius outside the composition root.* Because the swap is a one-line adapter selection behind a stable port, the rollback is the inverse one-line selection — no consumer code churns, the diff is reviewable in seconds, and the OneUptime rule "run the same test suite against both implementations" gives us a behavioral equivalence gate before we trust the real one.

### Pillar 3 — EXPAND / CONTRACT (parallel change): add-new → migrate → remove-old, releasable at every phase

**The pattern.** Break any backward-incompatible interface or schema change into three phases — **expand** (add the new alongside the old, both coexist), **migrate** (move every consumer/writer over, dual-write during the transition), **contract** (delete the old once nothing depends on it). The system is deployable after *each* phase ([Fowler — Parallel Change](https://martinfowler.com/bliki/ParallelChange.html), [Tim Wellhausen — zero-downtime persistent data](https://www.tim-wellhausen.de/papers/ExpandAndContract/ExpandAndContract.html), [Prisma Data Guide](https://www.prisma.io/dataguide/types/relational/expand-and-contract-pattern)). For DB: expand = add columns/tables non-destructively; migrate = backfill + dual-write trigger; contract = drop the old column after proving nothing reads it.

**Borjie application.** This is the rail for the **schema-touching waves** and the **immutable-migration hard rule** simultaneously. Migrations are append-only in Borjie *by law* — expand/contract is the only legal way to evolve a table. **Wave-4 prov-o + bi-temporal KG** (`postgres-kg-store.ts:171-181`, today a destructive `ON CONFLICT DO UPDATE`): expand = add the valid-time/`invalidatedAt` columns via a forward migration (they already exist in `temporal-entity-graph.schema.ts`); migrate = dual-path the upsert so it *both* overwrites (old readers) *and* writes the invalidate+insert (new readers) behind a flag; contract = remove the destructive overwrite once `GET /kg/{id}/history` and all readers use valid-time. **Wave-6 `/api/v1/modules`** needs "a forward migration recreating `modules/*`" — that is the expand phase of a parallel change, never an edit to the 0306 lane migration. **Wave-4 portal_tabs lost-update**: expand = add a real `row_version` column distinct from `schema_version`; migrate = start writing it + CAS on it; contract = remove the unguarded `save()`.

**Safety rail it adds.** *The immutable-migration invariant is satisfied by construction, and there is never a moment where the DB is in a non-deployable shape.* Backfill hazards are caught by the repo's existing `migration-safety-check.yml` (NOT NULL backfill validator) — expand always adds nullable/defaulted columns first, exactly what that gate enforces.

### Pillar 4 — PARALLEL RUN / DARK LAUNCH: run new + old together, compare outputs, cut over on match-rate

**The pattern.** Execute both code paths on real production traffic; always return the *old* result to the user; run the new path fire-and-forget; compare outputs and record a **match rate**; cut over only when match-rate and latency/error guardrails hold for a defined window ([Fowler — Dark Launching](https://martinfowler.com/bliki/DarkLaunching.html), [OneUptime, Jan 2026](https://oneuptime.com/blog/post/2026-01-30-dark-launch-patterns/view), [TechArchitect — Shadow Traffic & Dual-Run](https://www.techarchitectinsights.com/p/shadow-traffic-dual-run-prove-it-before-cutover)). The 2026 OneUptime numbers are concrete and adoptable as-is: **minMatchRate 0.99 early → 0.999 late**, sample 1% → 10% → 50% → 100%, max latency delta 50ms → 20ms, error-rate limit 0.1% → 0.01%, 24h → 48h dwell per phase, and the iron rule *"Never let dark path errors affect the user response. Wrap everything in try/catch."*

**Borjie application — this is how we flip the conductor (OK-1/OK-3/OK-4) without risking the paying turn.** The real arbiter/loop-runner/control-shell runs in **shadow** on the default `/ask` turn: the current fall-closed/stub behavior is served to the owner; the real conductor computes its `OrchestratorRequest`/`pickNext` dispatch in the background; we record whether the real topology decision *matches* the safe default's outcome and log every divergence. We do NOT cut a tenant over to live actuation until the shadow match-rate and the cost/latency deltas clear the OneUptime thresholds. For **OK-4 EstateMind actuator bridge**: the plan already says "emit an OrchestratorRequest IN ADDITION TO the nudge" — that addition is *literally a dark launch* (new actuator path runs beside the proven nudge path; nudge still fires; actuator effect gated until proven). For the **money/licence/deletion path the dark-launch is read-only** — the actuator saga's `dryRun` flag (OK-5's typed port) is the parallel-run primitive: run the saga in `dryRun`, compare its intended `PortAction[]` against the rule-based decision, never let it post to `LedgerService` until proven.

**Safety rail it adds.** *We get production-traffic proof that the awakened organ agrees with the safe incumbent before it can affect a paying user or a shilling.* The match-rate dashboard is the objective cut-over gate — no "it looked fine in staging." This is the rail that lets us honor *predictions APPEND never replace* (the new path is compared, not substituted) and *sovereign stays HITL* (dry-run never actuates).

### Pillar 5 — CHARACTERIZATION / GOLDEN-MASTER before touching anything

**The pattern.** Before you modify code lacking tests, pin its *current* behavior with characterization tests (a.k.a. golden master): observe outputs for given inputs, assert the observed output, so any unintended behavior change is caught. Coined by Michael Feathers — *"legacy code is simply code without tests"* — these are written *after* the code exists, to protect it during change ([Wikipedia — Characterization test](https://en.wikipedia.org/wiki/Characterization_test), [understandlegacycode.com](https://understandlegacycode.com/blog/key-points-of-working-effectively-with-legacy-code/), [Tech Lead Journal #195 — Feathers + AI assistants](https://techleadjournal.dev/episodes/195/)). Non-deterministic/volatile values must be masked.

**Borjie application.** Before we touch the destructive KG upsert, the dispatcher fall-closed branch, the consolidation null-wire, or the e-sig stub, we capture a golden master of the *current* live behavior: the exact response the stub/null-wire/deny-stub returns today (e.g. `NotYetWiredError` shape for `platform.run_consolidation_tick`; the deny payload from the `BORJIE_BODY_CHANGE`-off branch; the `ON CONFLICT DO UPDATE` row state). Then the real adapter must reproduce the *contract* (status codes, audit-row shape, error envelope) the system already depends on — divergence is a bug, not a feature. The repo already has the right gates to host these: `eval-orchestrator-scenarios.yml`, `kernel-eval.yml`, `trajectory-eval.yml` are characterization harnesses for the brain — extend them with a golden master per awakened organ. Mask the volatile bits the plan flags (timestamps, hash-chain digests, model nondeterminism) per the golden-master discipline.

**Safety rail it adds.** *We cannot silently change a behavior a paying integration already relies on.* The hash-chained audit-row shape, the four-eye envelope, the egress projection shape are all "current behavior" that golden masters freeze — protecting the invariants the closure plan must not regress (audit-chain append-only, sovereign HITL, no-IP-leak).

### Pillar 6 — PORTS & ADAPTERS / COMPOSITION ROOT / DI: swap the implementation, never the caller

**The pattern.** Ports declare what the domain needs; adapters provide concrete impls; the composition root wires them at startup; the domain never instantiates its own dependencies. *"Swapping [an adapter] requires zero changes to the domain… only the composition root needs to change"* ([Hexagonal Me](https://jmgarridopaz.github.io/content/hexagonalarchitecture.html), [Java Code Geeks, Jun 2025](https://www.javacodegeeks.com/2025/06/hexagonal-architecture-in-practice-ports-adapters-and-real-use-cases.html), [AWS Prescriptive Guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/hexagonal-architecture.html)).

**Borjie application — this is the closure plan's Principle 6 expressed as a change-safety rail.** Every awakening is "swap a driven adapter behind a port at the composition root." The proven in-repo template is `buildSemanticCachePort` / `buildIntentVerifierPort` at `sovereign.ts:631` — the closure plan says explicitly *"dark backend capabilities are wired as kernel ports (the proven pattern)… We never reach into a package's deep path from a route handler."* For **Wave-3** (anomaly/causal/belief/debate ports), **Wave-6** (`consolidationWorker` adapter forwarded into `createHqToolPortBindings`), **Wave-7** (`createGepgRealAdapter` into `hq-tool-port-bindings.ts`): the rail is *the only file that changes implementation is the composition root; the port type is the contract; the consumer is untouched.*

**Safety rail it adds.** *The change surface is minimized to one auditable location and the diff is a leaf swap, not a refactor.* This makes every awakening a small-reversible-commit (Pillar 7) and keeps the modular-monolith import discipline intact — no route handler grows a deep-path import, so the dependency-cruiser orphan baseline the closure plan tracks (≤16) cannot regress.

### Pillar 7 — IDEMPOTENT + REVERSIBLE STEP DESIGN + TRUNK-BASED SMALL-REVERSIBLE-COMMITS

**The pattern.** (a) Effects are exactly-once *by effect, not delivery*: give every intent an idempotency key, persist saga state, dedupe per key, compensate deterministically (idempotent compensation — running it N times == once) ([Umut Akbulut — provable SAGA compensation](https://medium.com/@umutt.akbulut/exactly-once-effect-does-it-really-exist-a-provable-design-for-saga-compensation-e81ccedb7f4e), [Gunnar Morling — On Idempotency Keys](https://www.morling.dev/blog/on-idempotency-keys/), [Idempotent-Saga pattern](https://medium.com/@toyezyadav/the-idempotent-saga-pattern-sagas-idempotency-keys-for-safe-workflows-5f7c7e1d5fb3)); each saga *step* gets its own key derived from the parent + step suffix. (b) Commit small, frequently, straight to a green trunk so a problem is a small diff and a revert is a one-move recovery ([trunkbaseddevelopment.com](https://trunkbaseddevelopment.com/continuous-integration/), [Atlassian](https://www.atlassian.com/continuous-delivery/continuous-integration/trunk-based-development)); incomplete work hides behind flags so the trunk stays deployable.

**Borjie application.** This pillar *is* closure-plan Principle 3 (durability is the substrate). **OK-5/OK-6**: the actuator port already carries `reversibility / idempotencyKey / dryRun / confirm / compensate` *in the type*, so "at-least-once delivery × idempotent effect = exactly-once-effect" falls out of the type system, and `irreversible ⇒ requiresApproval ⇒ four-eye` is type-enforced. The executor-fleet discipline is the trunk-based rail: each awakening is one verified-then-commit on a clean tree behind its existing flag (`DURABLE_EXEC_ENABLED`, `BORJIE_MODALITY_ARBITER`, `BORJIE_BODY_CHANGE`), so the trunk is always shippable and any single awakening reverts in one move. Per-step keys derived from the parent (`parentKey:stepName`) make the four-eye queue + ledger publisher durable via the existing `DurableEventPublisher.enqueueToOutbox(events, tx)`.

**Safety rail it adds.** *A retried or restarted awakening never double-posts to the ledger and never half-files a licence; a bad awakening reverts in one commit.* This is the rail that makes the money-path and webhook-at-least-once invariants hold under the new durable substrate.

## PART II — THE STAGED-AUTONOMY OVERLAY (the AI-specific layer, 2026)

Borjie is not a CRUD app; the dark organs *actuate*. The 2025–2026 agent-safety canon adds one overlay on top of the seven pillars: **shadow-mode → staged autonomy.** *"Start agents in shadow mode where they analyze but don't act, then gradually enable through flags for specific services, cohorts, or regions… each expansion depending on proven safe behavior from the previous stage"* ([Brightlume — Shadow-Mode Rollouts for AI Agents](https://brightlume.ai/blog/shadow-lume-rollouts-ai-agents-pilot-production), [DevOps.com — Guardrails to Safely Deploy AI Agents](https://devops.com/before-you-go-agentic-top-guardrails-to-safely-deploy-ai-agents-in-observability/), [Eduonix — HITL design, Feb 2026](https://blog.eduonix.com/2026/02/autonomous-ai-systems-human-in-the-loop-design/)). The pattern's exemplar — *"start with low-stakes decisions (claims under $1,000), monitor 2 weeks, then expand to higher-stakes"* — maps directly to a `confidence × (1−reversibility)` autonomy gate.

**Borjie application — the awakening ladder for every actuating organ (EstateMind OK-4, the arbiter OK-1, the saga OK-5):**

1. **SENSE-ONLY (today).** EstateMind writes a `proactive_nudge` row. Arbiter falls closed. Saga is unbuilt. This is the safe floor.
2. **SHADOW.** Real conductor runs, computes its decision, writes a *decision-log* entry on the internal plane only, but the *effect* is suppressed (`dryRun:true`). Match-rate measured vs the rule-based incumbent (Pillar 4).
3. **LOW-STAKES LIVE.** Flip the flag for one canary tenant, *reversible* actions only (`reversibility=reversible`, below the `confidence × (1−reversibility)` bar). HITL still required for anything sovereign.
4. **WIDEN.** Raise the slice (more tenants / higher confidence band) only while match-rate ≥ 0.999 and cost/latency deltas hold.
5. **HIGH-STAKES STAYS HITL FOREVER.** Money / licence / deletion / four-eye never leave human approval — staged autonomy *widens the reversible surface*, it never removes the sovereign gate. This is the non-negotiable ceiling.

**Safety rail it adds.** *Autonomy is earned per-organ on measured evidence and capped below the sovereign line by the type system, not by reviewer vigilance.* This is the rail that reconciles "the resident Mind becomes an actuator" with "sovereign stays HITL."

## PART III — THE ONE RITUAL (apply to every gap, every wave)

Every awakening — stub→real, null-wire→adapter, deny-stub→authorizer, dark→flag-on — runs the SAME seven-step ritual. This is the executor-fleet's operating loop; deviating from it is how we'd fail.

| Step | Move | Pillar | In-repo gate / artifact |
|---|---|---|---|
| **1. PIN** | Golden-master the *current* stub/null/deny behavior (status, audit-row shape, error envelope). | Characterization (P5) | new eval case in `eval-orchestrator-scenarios.yml` / `kernel-eval.yml` |
| **2. ABSTRACT** | Confirm the port exists; if not, add the port type FIRST (no impl). Old + new will live behind it. | Ports/Adapters (P6) | `kernel/` port, `sovereign.ts:631` template |
| **3. EXPAND** | Add the real adapter + any schema columns *additively* (new migration, never edit). Both coexist. | Expand/Contract (P3) | forward migration; `migration-safety-check.yml` |
| **4. SHADOW** | Wire the real adapter behind its flag, default-OFF; run it in parallel-run/`dryRun`; record match-rate vs incumbent. | Parallel-run + Staged autonomy (P4 + Part II) | flag (`BORJIE_*`), match-rate dashboard, decision-log |
| **5. CANARY** | Flip the flag for one tenant/slice; reversible effects only; widen on thresholds (0.99→0.999, 1%→100%). | Strangler + Progressive delivery (P1) | per-tenant override; kill-switch flag |
| **6. PROVE** | Reachability test (organ executes on a live path) + membrane assertion (egress/policy/four-eye where crossed) + relevant CI eval green. | Closure-plan Part V | `audit-not-yet-wired.yml`=0, dep-cruiser ≤16 |
| **7. CONTRACT** | After ≥1 release cycle at 100% with no divergence, delete the stub + dead flag (kill flag-debt). | Expand/Contract + Branch-by-abstraction (P3 + P2) | small-reversible-commit on green trunk |

**Two hard "never" rules baked into the ritual (from the 2026 sources):**
- **Never combine variables in one slice.** *"If you change code, schema, cache keys, and configuration together, root cause is impossible — deploy in slices"* ([Unleash / progressive delivery 2026](https://www.getunleash.io/blog/canary-release-vs-progressive-delivery), [DigitalApplied — Feature Flag Rollout Strategies 2026](https://www.digitalapplied.com/blog/feature-flag-rollout-strategies-2026-engineering-playbook)). So: migration lands and bakes *before* the adapter flips; the adapter flips *before* the arbiter routes to it. One variable per commit.
- **Never leave the flag forever.** Release/ops flags are temporary; un-removed flags are flag-debt that bloats and confuses ([DigitalApplied 2026](https://www.digitalapplied.com/blog/feature-flag-rollout-strategies-2026-engineering-playbook), [LaunchDarkly — Dark Launching](https://launchdarkly.com/blog/guide-to-dark-launching/)). Step 7 (CONTRACT) is mandatory, not optional. The *only* permanent flags are kill-switches (which Borjie already treats as fail-closed permanent ops controls).

## PART V — THE FIVE THINGS THAT WOULD MAKE US FAIL (anti-patterns to forbid)

1. **Big-bang flag flip on the default turn.** Flipping `BORJIE_MODALITY_ARBITER` to default-ON for *all* tenants at once, skipping shadow + canary. → Forbidden by Pillar 1/4; use the awakening ladder.
2. **Editing call sites instead of swapping the adapter.** Reaching into a package's deep path from a route handler to "just wire it." → Violates Pillar 6 + the modular-monolith rule; the dep-cruiser baseline catches it.
3. **Bundling variables in one commit.** Migration + adapter + arbiter route in one PR makes root-cause impossible ([2026 progressive-delivery guidance](https://www.digitalapplied.com/blog/feature-flag-rollout-strategies-2026-engineering-playbook)). → One variable per slice; migration bakes first.
4. **Editing a shipped migration to "fix" the schema.** → Violates the immutable-migration hard rule; expand/contract with a *new* forward migration is the only path.
5. **Leaving the stub + flag in after 100% cutover.** Flag-debt + dead stub = the next engineer can't tell live from dead. → Step 7 CONTRACT is mandatory; only kill-switches are permanent.

## PART VI — DEFINITION OF SAFE-DONE (per awakened organ)

An organ is safely awakened when ALL hold: (1) **PIN** golden-master recorded and the real adapter reproduces the depended-on contract; (2) **SHADOW** match-rate ≥0.999 vs incumbent with latency/error deltas inside the OneUptime thresholds; (3) **MEMBRANE** asserted where the wave crosses egress / policy / four-eye (no IP leak, sovereign HITL intact); (4) **REVERSIBILITY** proven — the awakening reverts in one commit and the effect is idempotent/compensable; (5) **CI green** — `audit-not-yet-wired`=0, dep-cruiser ≤16, the relevant kernel/orchestrator/trajectory eval green; (6) **CONTRACT** — stub + temporary flag deleted on a green trunk. When all ten waves clear this bar, the 43 organs are live on real user paths with *zero* mandate invariant regressed — which is the only definition of "never failed at the wiring" the owner directive accepts.
